# MakersVault v5.1 Release Scope

This is the scope of the frozen Gate 5 candidate at `f6ff55b`. Later local Gates
6–11E implement roadmap features beyond that baseline, including shared-vault
accounts and passkey MFA. Their current evidence is in the
[architecture runbook](ARCHITECTURE_RUNBOOK.md); those gates do not silently replace
the frozen release candidate or authorize publication.

## Release objective

v5.1 is a confidence release focused on performance, daily usability, safe
self-hosting, and visible product polish.

The release should feel dramatically better without attempting the full future
Project -> Artifact -> Revision architecture.

## Release promises

### 1. Fast and resilient

The library remains responsive as it grows and does not render every full model at
once.

### 2. Easy to organize at scale

Folder navigation, selection, bulk work, and mounted-library ingestion are clear
and predictable.

### 3. Models have useful context

Models have human-readable identity, metadata, supporting documents, and automatic
prepared-print summaries without exposing machine payloads.

### 4. A vault users can trust

Authentication defaults, migration behavior, backups, and release artifacts are
handled deliberately.

## Already established in the v5.1 working version

- Modern nested folder sidebar with folder search.
- Human-readable model names unique within a folder.
- Filename updates when the model name changes.
- Creator, collection, tags, and notes.
- Configurable managed-storage templates.
- Lazy card previews, embedded 3MF thumbnail extraction, persistent generated
  thumbnails, and configurable preview modes.
- Pagination and incremental library loading.
- Mounted-folder import with copy and no-copy modes.
- ZIP and source-site import workflows.
- Multi-item download, tag editing, and deletion behavior.
- Open-in-slicer and LightBurn bridge workflows.
- Visible supporting documents grouped with a model.
- Hidden prepared-print payloads with automatic printer, material, nozzle, layer,
  and duration extraction when available.
- Prepared-print handoff through the configured slicer without slicing or printer
  control.

These features still require release-level regression testing and may need polish.

## P0 — release requirements

### Performance and preview guardrails

- Define a repeatable benchmark library containing small, medium, large, malformed,
  and multi-plate files.
- Record initial load time, card responsiveness, preview throughput, and memory use.
- Do not automatically attempt expensive previews above a documented safety limit.
- Time out or abort preview work that does not complete within its budget.
- Persist failed preview state and offer an explicit retry.
- Keep full interactive rendering behind opening an individual model.
- Confirm that cached thumbnails prevent repeated model parsing across clients.

Acceptance criteria:

- A problematic model cannot freeze navigation for the rest of the library.
- Only bounded preview work is active at one time.
- Returning to an already processed library predominantly loads static thumbnails.
- The benchmark results are recorded with the release notes.

### Bulk workflow polish

- Add a visible toolbar whenever one or more models are selected.
- Show the number of selected models.
- Support select current page and clear selection.
- Support bulk move, tagging, download, and conservative deletion.
- Show progress and summarize partial failures.
- Keep selection behavior understandable across filtering and pagination.

Acceptance criteria:

- Users do not need to edit one selected card to discover bulk operations.
- Bulk actions clearly state whether they apply to the current page or selected IDs.
- Destructive actions require explicit confirmation.

Selecting every server-side match is deferred until the API supports bulk
operations without loading thousands of IDs into the browser.

### Folder location and navigation

- Show a breadcrumb for the active folder.
- Keep nested hierarchy and folder search fast.
- Make the current folder unmistakable.
- Provide useful empty states for a folder with subfolders but no direct models.

Acceptance criteria:

- A user can understand their current location without relying solely on sidebar
  indentation.
- Breadcrumb segments navigate to their corresponding folder.

### Mounted-library observability

- Add a deliberate rescan action.
- Show the last scan time and its status.
- Report imported, skipped, and failed counts.
- Provide failure details without requiring container-log access.
- Preserve source files and never silently reorganize a mounted no-copy library.
- Make copy versus index-in-place behavior clear before scanning.

Acceptance criteria:

- A user can tell whether a scan completed and what happened.
- Repeated scans do not create duplicate entries for unchanged source paths.
- A failed file does not abort the entire scan.

Live per-file progress, sophisticated exclusion rules, and continuous NAS watching
may follow after v5.1.

### Authentication and deployment hardening

- Do not quietly operate with published default credentials or a default signing
  secret.
- Provide a safe first-run or explicit-environment configuration path.
- Surface configuration problems clearly at startup.
- Document secure reverse-proxy and remote-access expectations.
- Preserve existing deployments through a documented migration path.

Acceptance criteria:

- A fresh production deployment cannot unknowingly retain known credentials.
- Authentication tokens use a deployment-specific secret.
- Upgrade instructions explain any required environment changes.

Multi-user accounts, roles, MFA, API keys, and OIDC are a separate security project
and are not requirements of the frozen v5.1 candidate. Gate 11 and Gate 11E now
implement the account/role/session/audit/recovery and passkey portions in later local
history; API keys and OIDC remain separately gated.

### Backup, migration, and recovery documentation

- Document exactly which database and storage paths must be backed up.
- Provide tested stop, backup, restore, and upgrade procedures.
- Test the v5.1 database migration against a representative pre-v5.1 library.
- State which generated artifacts can be recreated and which data is essential.
- Document how mounted no-copy files affect backup completeness.

Acceptance criteria:

- A test instance can be restored to another clean installation using the
  documented procedure.
- Existing primary files, metadata, thumbnails, supporting files, and hidden
  prepared-print records survive an upgrade.

### Release and repository hygiene

- Add or update the changelog, release notes, security policy, contribution guide,
  and issue templates.
- Exclude runtime databases, Python caches, and other generated content from future
  commits where practical.
- Run automated API and web builds.
- Add focused tests for migrations, model bundles, prepared-print visibility, and
  preview behavior.
- Publish versioned Docker and bridge artifacts with clear upgrade notes.

## P1 — include when stable

### Content identity

- Compute SHA-256 while ingesting new primary and related files.
- Backfill existing managed files in bounded background work.
- Warn about matching content without automatically deleting or merging records.
- Record hashing failures and permit retry.

This establishes rename-resistant identity for duplicate detection, revisions,
integrity checks, and future backups.

### Provenance metadata

- Store source URL when importing from a supported site.
- Add license metadata when it can be extracted reliably or entered manually.
- Preserve creator information supplied by the source when appropriate.
- Search the new provenance fields.

### UI consistency

- Improve loading, error, and empty states across all themes.
- Keep card density usable after adding metadata and supporting-file controls.
- Verify common tablet and narrow-desktop layouts.
- Use consistent language for models, files, prepared prints, and applications.

### LightBurn and bridge polish

- Verify `.lbrn` and `.lbrn2` handoff on supported desktop platforms.
- Keep installation and troubleshooting instructions current.
- Use consistent bridge logging and error guidance.

## Explicit v5.1 non-goals

- MakersVault does not slice models.
- MakersVault does not send jobs to machines or start fabrication.
- No visible G-code browser or normal G-code download workflow.
- No manual thumbnail upload.
- No full Project -> Artifact -> Revision rewrite.
- No temporary `AssetGroup` entity.
- No multi-user/MFA/SSO implementation in the frozen candidate.
- No print-farm scheduling, filament accounting, or printer telemetry.
- No public plugin or application-adapter SDK.
- No cloud-storage or paid-service dependency.

## Release decision rule

P0 reliability work takes precedence over P1 metadata and architecture work. A
feature that cannot be migrated, tested, explained, and recovered safely should
not block the release.

The release is ready when users can upgrade an existing library, browse it without
expensive preview stalls, organize many models through clear bulk workflows,
understand mounted-import results, and restore the vault using documented steps.
